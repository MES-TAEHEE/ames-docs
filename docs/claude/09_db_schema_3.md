# DB 스키마 영역·마이그레이션 노트 (3/5)

> `CLAUDE.md` 에서 분리한 상세 문서입니다(원문 그대로, 11-18 토큰 절감 정리). 필요한 주제만 `grep -rn 키워드 docs/claude/` 로 찾아 해당 줄 범위만 읽으세요.

BOM 버전 상태(`MD_BomVersion.Status`)는 공통코드 **`BOM_STATUS`**(DRAFT 초안·PENDING 승인 대기·APPROVED 승인·REJECTED 반려·EXPIRED 만료)이고 `dist/migrate_bom_status_code.sql`(10-02, 순서 무관·재실행 안전)이 만든다. 종료일(`EffTo`)이 오늘(DB 날짜)보다 지난 APPROVED 버전은 MD-004 가 목록을 읽을 때마다 `MasterDataRepository.ExpireBomVersions` 로 **EXPIRED** 로 바꾸고 감사 `EXPIRE` 를 남긴다(마이그레이션도 1회 같은 처리). 버전 규칙 정본은 `AMES.Data.Services.BomVersionRules`(대표 버전·승인 시 겹치는 기존 승인 버전 종료일을 새 시작일 전날로 마감·새 버전 기본 시작일 = 직전 버전 종료일 다음 날(지난 날이면 오늘)·버전 번호 `V{주}.{부}` 정규화, 테스트 `BomVersionRulesTests`) — MRP·코어 해석·BOP 상하위(`BomHierarchy`)는 기간으로 유효 버전을 고르므로 EXPIRED 와 무관하다. **MD-004 버전 등록은 시작일(필수)·종료일을 오늘(DB 날짜)부터만** 받는다(10-20 사용자 요청 — 달력 `Min` 으로 지난 날을 막고, 직접 입력한 지난 날은 달력이 지워 시작일 필수로 저장 전에 거부; 수정 창·저장소는 제한하지 않는다). **BOM 라인(추가·수정·삭제·재활성화)은 버전이 DRAFT 일 때만 바뀐다**(10-10 사용자 결정 — 승인 요청·승인 뒤에는 고칠 수 없고 새 버전으로 바꾼다): `MasterDataRepository.InsertBomLine/UpdateBomLine/DeleteBomLine/ReactivateBomLine` 이 버전 행을 UPDLOCK 으로 잡은 같은 문장에서 `Status='DRAFT'` 를 보고 0행이면 false, MD-004 는 수정 창을 닫고 버전을 새로 읽어 "다른 사용자가 이미 상태를 바꿈" 안내(감사 없음) — 정본 테스트 `BomLineDraftOnlyTests`. **BOM 라인 단위(`MD_Bom.UOM`)는 구성품의 기본 단위(`MD_Item.DefaultUOM`)를 그대로 저장한다**(10-23 사용자 요청): `InsertBomLine`·`UpdateBomLine`·엑셀 올리기(`ImportBomVersion`)는 단위를 받지 않고 품목에서 읽어 쓰며(구성품을 바꾸면 그 품번 단위), MD-004 라인 창의 단위 칸은 읽기 전용 표시와 안내(`MD.Bom.Hint.UomFromItem`)뿐이다. **품목 단위를 바꾸면 그 품목을 구성품으로 쓰는 BOM 라인(모든 버전 — 승인·만료 포함)의 단위도 같은 트랜잭션에서 바뀐다**(`UpdateItem` 이 바꾼 라인 수를 돌려주고, MD-003 은 저장 안내에 건수를 덧붙이며 감사 `MD-003/BOM_UOM_SYNC` 를 남긴다, 수정 창 안내 `MD.Items.Hint.UomSyncsBom`). 수량(`QtyPer`)은 환산하지 않는다. 정본 테스트 `BomUomFollowsItemTests`(로컬 DB 쓰기). **품목 기본 단위는 재고·실적이 있으면 바꿀 수 없다**(10-20 사용자 요청 — 재고 = 수량 0 아닌 `WH_Inventory` 행, 실적 = 그 품번 LOT 의 `PR_ProductionResult` 또는 자동 차감 `WH_InventoryTransaction.SourceType='BACKFLUSH'`, 판정 `MasterDataRepository.ItemUomInUse`, SQL 조각 `ItemStockOrResultSql`): MD-003 수정 창은 재고·실적이 있는 품목의 단위 콤보를 끄고 안내(`MD.Items.Hint.UomLocked`)를 보이며, `UpdateItem` 도 단위 변경을 `ItemUomLockedException`(SQL 51832)으로 거부한다(다른 값 수정은 그대로) — 정본 테스트 `ItemUomLockTests`(로컬 DB 쓰기). 마이그레이션 없이 신 Web 을 올리면 상태 콤보가 "전체" 뿐이고 배지는 코드값 그대로 보일 뿐 예외는 없다.
생산 마감일 컬럼 `PP_WorkOrder.ProdDeadline` 과 설정 `SYS_Config.PP_PROD_BUFFER_WORKDAYS`(기본 3, 1 이상만 유효 — 0·미등록·파싱 실패는 3 으로 본다) 는 `dist/migrate_wo_prod_deadline.sql` — 순서 무관, 재실행 안전. PP-003 이 WO 를 만들 때 `납기 − 버퍼 근무일`(`SYS_FactoryCalendar` 의 WORKDAY·SPECIAL 만 근무일, 행 없는 날은 토·일만 휴일) 을 박아 두고(PP-CAL 에서 납기를 바꾸면 같은 규칙·현재 버퍼로 다시 계산하고 수정자·시각을 남긴다 — 10-09, `WorkOrderRepository.UpdateDueDate`, 없는 WO 와 **끝난 WO(완료·입고·마감·취소 — 정본 `AMES.Data.Services.WoStatusRules`, MRP·APS 의 열린 WO 기준과 같은 목록, 10-14)** 는 행을 잡고 확인해 바꾸지 않고 사유별로 안내하며, 상세 창도 끝난 WO 에는 「납기 변경」 대신 안내를 보인다 — 정본 테스트 `WoStatusRulesTests`), `AMES.Data.Scheduling.DeadlinePacker` 가 오늘부터 마감일까지 단계별·날짜별로 수량을 쪼개 자동 배치한다(마감일 초과분은 납기일까지 `Late`, 그래도 남으면 `Shortfall`; 납기가 이미 지난 수주는 오늘부터 60일 안에 전량 `Late` 로 넣는다). 이 마이그레이션 없이 신 Web 을 올리면 PP-003 배치뿐 아니라 `WorkOrderRepository.ListAll` 을 쓰는 PP-004·PP-CAL 도 매번 예외다.
백필된 WO 중 헤더 라인이 마지막 라인 단계가 아닌 건(예: A 라우팅을 INJ 라인으로 발행)은 첫 후속 실적에서 헤더 `CompletedQty` 가 마지막 단계 값으로 내려갈 수 있다 — PP-04 진척률이 한 번 감소해 보인다.
**PP-004 WO 취소는 실적이 있는 단계가 없을 때만**(헤더·단계 UPDLOCK 확인 — POP 확정과 겹치면 한쪽씩) 되고 오늘부터의 슬롯만 지운다(지난 슬롯은 일정 준수용으로 남김). APS 가 만든 WO 면 같은 트랜잭션에서 그 계획 행(`PP_ApsPlanLine.WoID` 이거나 `PP_ApsRunWo` 로 이어진 행)의 연결을 풀고 Released 실행을 Saved 로 되돌린다(10-28 — 같은 실행에서 다시 「WO 생성」하면 남은 조각의 슬롯을 빼고 취소한 몫만 나온다, 정본 `ApsWoCreateTests.Cancelling_an_aps_wo_…`). 진행 중(In Progress) WO 는 「강제 마감」(승인 권한 A, `WorkOrderRepository.ForceCloseWo`, 감사 `PP-004/FORCE_CLOSE`)으로 헤더·남은 단계를 Closed 로 하고 내일부터의 슬롯을 지운다(10-27). PP-003 순수요의 완제품 재고도 위치 무관(10-27 — 전에는 FG 구역만). **WO 생성(PP-003 일괄·PP-APS)은 앱 잠금 `AMES-PP-WO-CREATE`(`PpRepository.LockWoCreation`)로 한 번에 하나**(10-27 — 수주 잔량을 읽고 나서 채번 잠금을 잡아 동시에 돌면 같은 수주를 초과 배정했다). **PP-003 은 같은 금형·색상의 형제 품번(LH/RH)이 이 일괄 생성 안에서 앞 수주 슬롯에 전량 덮이면 0분 슬롯으로 얹는다**(10-27, `TryRideSiblings` — APS 형제 규칙과 같음, 일부만 덮이면 종전대로 시간을 잡는다). PP-003 일괄 생성은 WO 생성 → Release(단계별 라인) → 단계마다 PP_LineSchedule 슬롯(DRAFT) 배치까지 **한 트랜잭션**으로 처리한다(PpRepository.CreateScheduledWorkOrders). 수량 기준은 순수요·수주량·**직접 입력** 세 가지이고, 순수요/수주량은 **기발행 WO 수량(취소 제외)을 뺀 잔량**이다 — 같은 수주에 WO 를 나눠 낼 수 있고(`PlanLineRow.IssuedQty/RemainQty`, 잔량 > 0 인 수주만 후보), 직접 입력은 `OrderPlan.Qty` 로 서버에 그대로 전달되며 수주량 초과도 허용한다(다이얼로그에 경고만). 수주 1건 = WO 1건 제약은 없어졌다. 배치 위치·날짜·수량은 AMES.Data.Scheduling.DeadlinePacker(순수 함수, 하루 안은 SlotPacker.FillDay)가 정하고, 하루 능력은 LineScheduleRepository.GetDayCapacity(패턴 해석: 그 날 저장 행 → 라인 전용 ACTIVE → 전역)로 읽는다. 자리가 없는 단계는 슬롯 없이 Released 로 남아 PP-LSB 보드의 미배치 목록에서 수동 배치한다. 수동 배치 창의 계획 수량 기본값은 **그 라인에 아직 배치되지 않은 수량**(`OpenQty` − 그 라인 다른 날짜에 이미 놓인 그 WO 슬롯 수량, 시간을 점유한 슬롯만 — `LineScheduleRepository.WoRow.UnplacedQty`)이고 이미 놓인 수량이 있으면 안내가 보인다(10-13 — 전에는 매번 `OpenQty` 전량이라 고치지 않으면 이중 계획이 됐다). `OpenQty` 는 WO 생성 때 주문 수량으로 채운 뒤 바뀌지 않는다. Pop INJ-MAIN 은 오늘 슬롯을 계획으로 읽으므로, 이 경로가 아니면 WO 가 Pop 에 안 뜬다.
**WO 번호 유니크 인덱스 `UX_PP_WorkOrder_WoNumber`**(10-22, `dist/migrate_wonumber_unique.sql` — 순서 무관·재실행 안전, 같은 번호 행이나 NULL 행이 2건 이상이면 목록을 보이고 중단, 10-22 개발서버 적용, 스키마·`rebuild_db.sh` 반영): WO 채번 `PpRepository.NextWoSeq`(PP-003 일괄 생성·PP-APS WO 생성·미리보기 dryRun 공용)는 `WoNumber LIKE '{접두어}%'` 를 UPDLOCK·HOLDLOCK 으로 잡는데, 인덱스가 없을 때는 이 범위 잠금이 테이블 전체에 걸려 채번 트랜잭션이 도는 동안 POP 스캔 확정(`BumpStepCompleted` 의 PP_WorkOrder UPDATE)이 기다리다 30초를 넘기면 실패했다. 인덱스가 있으면 잠금이 그 날 접두어(`WO-yyyyMMdd-`) 키 범위에만 걸리고 POP 갱신은 WoNumber 를 바꾸지 않아 기다리지 않는다(10-22 개발 DB 실측 — 범위 잠금 보유 중 같은 접두어 WO 갱신 즉시 완료). **필터 인덱스(`WHERE WoNumber IS NOT NULL`)로 두지 않았다** — 필터 인덱스는 그 테이블을 고치는 모든 연결에 `QUOTED_IDENTIFIER ON` 을 요구해(Msg 1934) `-I` 없는 sqlcmd DML 이 깨진다; 대신 NULL 은 한 행까지만 허용되며 앱 코드는 WoNumber 를 항상 채운다. 테스트 픽스처가 고정 번호(`ITEST-APS-W0` 등)를 넣으므로 실패한 테스트가 행을 남기면 다음 실행이 중복 키로 막힐 수 있다 — 그 행을 지우고 다시 돌린다.
**PP-LSB 「발행」은 폐지됐다**(10-14 사용자 결정 — 결과를 읽는 곳이 화면·쓰지 않는 Api·MD 삭제 검사뿐이었다): 저장은 「적용」(`LineScheduleRepository.SaveSchedule`, Status `DRAFT` = 공통코드 `SCHEDULE_STATUS` 「적용됨」) 하나이고, 「초기화」는 그 라인·날짜 행을 전부 지운다(발행 행 보존 없음). 발행 버튼·`PublishSchedule`·분 단위 스냅샷·`PP_ProductionCalendarOverride` 테이블·`PP_LineSchedule.PublishedAt/PublishedBy`·Api `GET /api/pp/calendar`·MD 삭제 사용처 「발행 기록」을 없앴고, PP-LSB 화면 기본 권한은 `__X`(승인 기능 없음) — `dist/migrate_lsb_publish_removal.sql`(재실행 안전, PUBLISHED → DRAFT·컬럼/테이블 삭제·공통코드·권한, `rebuild_db.sh` 의 권한 마이그레이션 다음). **신 Web·Api 를 먼저 올리고 이 마이그레이션을 적용한다** — 구 Web 은 `PublishedAt` 을 읽어 마이그레이션 뒤에는 PP-LSB 가 열리지 않는다(신 바이너리는 구 DB 에서도 동작). 옛 `migrate_calendaroverride_snapshot.sql` 은 테이블이 없으면 건너뛴다. **POP PLAN 은 「적용」된 슬롯을 그대로 읽는다**(10-28 사용자 결정 — 기준 유지: 「적용」만 해도 현장 PLAN 에 바로 반영되며, 10-09 에 발행 기준으로 바꾸려던 안은 폐기).
**PP-OEE 스냅샷(`PP_LineOEE`)은 (라인, 일자, 교대) 키당 1행이다**(10-14): `OeeRepository.SaveSnapshot` 이 한 트랜잭션에서 그 키를 `UPDLOCK, HOLDLOCK` 으로 읽고 있으면 그 행을 덮어쓰고 없으면 새로 만들며, 결과 `SnapshotSaveResult(Id, Created, Before)` 로 감사(새 행 Created · 덮어쓰기 Updated + 이전 값)를 남긴다 — 전에는 잠금 없이 UPDATE 0행이면 INSERT 해 동시 저장 때 같은 키 행이 2개 생겼다. 마지막 안전망은 유니크 인덱스 `UX_PP_LineOEE_Line_Date_Shift`(교대 NULL 인 일 단위도 키당 1행) — `dist/migrate_pp_lineoee_unique.sql`(재실행 안전, 같은 키 행이 있으면 목록을 보이고 중단, 10-14 개발·로컬 적용, 스키마·`rebuild_db.sh` 반영, 순서 무관). 정본 테스트 `OeeSnapshotSaveTests`(로컬 DB 쓰기, 단독 실행 컬렉션).

예비품 마스터·입출고(`MD_SparePart` · `MNT_SparePartsTxn`)는 마이그레이션 3개를 **이 순서로** 적용한다: ① `dist/migrate_spare_part_category.sql`(공통코드 `SPAREPARTS_CATEGORY` A~K 1자리 교체 · `SPAREPARTS_EQUIP` 1~9 신설 · `Category` VARCHAR(1) · `ApplicableEquip` 추가 · `CompatEquipJSON` 삭제) → ② `dist/migrate_spare_part_no.sql`(`SparePartNo VARCHAR(16)` 첫 컬럼, 기존 행 채번 백필) → ③ `dist/migrate_spare_part_pk.sql`(**PK 를 `SparePartNo` 로**, `PartNo` 는 고유 인덱스, 현재고 `OnHandQty` 추가, `MNT_SparePartsTxn` 을 `SparePartNo` 논리 참조(**FK 없음**, 사용자 결정) + `BalanceBefore/BalanceAfter` 스냅샷만 남기는 구조로 재생성, 거래 단가(`UnitPrice`)도 제거 — 재고 금액은 마스터 `UnitCost` × 현재고). 셋 다 가드형·재실행 안전이며 컬럼 순서 때문에 테이블을 재생성하므로 확인용 SELECT 는 `GO` 뒤 별도 배치에 둔다. 예비품번호는 `MasterDataRepository.InsertSparePart` 가 `EOS-SP-{분류}{적용설비}-{yy}{순번4}` 로 트랜잭션 안에서 채번(분류·적용설비 필수, 등록 후 불변, **순번 9999 는 PDA 테스트 고정 데이터 `EOS-SP-K9-269999`(`dist/pda/PDA_SCHEMA.sql`) 몫이라 MAX 에서 제외, 9998 을 넘으면 예외** — 09-16 에 9999 를 포함해 채번한 10000 이 VARCHAR(16) 에서 잘려 `EOS-SP-K9-261000` 이 등록된 사고의 재발 방지)하고, 현재고는 `MntRepository.AdjustSparePartStock`(IN/OUT/ADJ, 마스터 갱신 + 이력 INSERT 한 트랜잭션, 재고 부족 출고 거부)와 PDA 시리얼 입출고(`PdaSparePartsSql` — 10-16 프로시저에서 앱 SQL 로 전환)로만 바뀐다(보전 작업지시의 사용 부품도 PDA 출고 — 아래 MNT 규칙 ⑥). 이력이 있는 부품과 PM 템플릿 점검 단계(MD-027)가 필요 부품으로 쓰는 부품은 `DeleteSparePart` 가 거부한다(FK 가 없으므로 고아 방지 책임이 리포지토리에 있다 — 비활성 처리로 안내). 입출고 전용 화면은 아직 없고(MNT-08 입고 보류 항목), MD-026 등록 화면의 초기 재고는 `InsertSparePart(…, initialQty)` 가 채번·INSERT 와 같은 트랜잭션에서 같은 모양의 IN 이력(RefType ADJ)으로 남긴다(10-12 — 전에는 등록 뒤 따로 입고해 실패하면 재고 0 인 부품만 남았다). 부품 이미지는 ④ `dist/migrate_spare_part_image.sql`(`SparePartImage VARBINARY(MAX)` 를 `UnitCost` 다음에 — 컬럼 순서 때문에 재생성, 재실행 안전) 로 두며, MD-026 이 `InputFile` + `RequestImageFileAsync` 로 **브라우저에서 320×180 이내(비율 유지)로 축소한 JPEG/PNG 바이트만** 저장한다(PNG 는 투명 유지). 목록 조회는 바이트를 싣지 않고 `HasImage` 만 읽어 체크 아이콘(BOP QC 열과 동일)으로 유무만 보이며, 이미지 자체는 수정 모달에서 본다. 이미지 교체/제거는 `UpdateSparePart(…, imageChanged, image)` 가 같은 UPDATE 에서 바뀐 경우에만 쓴다(10-12 — 따로 쓰던 `UpdateSparePartImage` 는 삭제). MD-026 감사는 저장이 끝난 뒤 한 번 남기며 이미지는 바꿨을 때만 전/후 크기(`AuditLogger.Patch`)로 남긴다. 보관 구역·칸은 ⑤ `dist/migrate_spare_part_zone_slot.sql`(`ZoneCode VARCHAR(20)` · `Slot VARCHAR(5)` 를 `SparePartImage` 다음에 — `MD_Location` 과 같은 형, 재생성·재실행 안전, 공통코드 `MNT_ZONE`·`MNT_SLOT` 그룹/항목도 없으면 생성) 로 두며 MD-026 이 두 공통코드 콤보로 관리한다. 자유 입력이던 `StorageLoc` 컬럼은 같은 마이그레이션이 삭제한다(구역·칸이 대체). 제조사 `Maker NVARCHAR(100)`(자유 입력, `SupplierID` 앞)은 ⑥ `dist/migrate_spare_part_maker.sql`(재생성·재실행 안전). 자유 입력 위치 `ExtraLocation NVARCHAR(60)`(`Slot` 다음)은 ⑦ `dist/migrate_spare_part_extra_location.sql`(재생성·재실행 안전, 공통코드 `MNT_SLOT` 에 `EX`(Extra) 추가) — **구역 `SP_EXTRA` 는 칸이 `EX` 로 고정되고 `ExtraLocation` 은 그 구역에서만 쓴다**(정본 `MasterDataRepository.NormalizeSpareLocation`, 테스트 `SpareLocationRuleTests`; 다른 구역이면 `EX` 칸·자유 위치를 저장 직전에 지운다). MD-026 은 구역을 `SP_EXTRA` 로 고르면 칸을 `EX` 로 채워 비활성화하고 입력란을 보이며, 다른 구역에서는 `EX` 를 칸 옵션에서 뺀다. **PDA API 는 예비품 위치를 `MD_Location` 과 (`ZoneCode`, `Slot`) 으로 맞추므로** 같은 마이그레이션이 기존 `SP_EXTRA` 예비품과 `MD_Location` 의 `SP-EXTRA` 행 칸도 `EX` 로 맞추고, `dist/pda/PDA_SEED.sql`·`PDA_SCHEMA.sql`(테스트 리셋 프로시저)의 해당 값도 `EX` 다 — 한쪽만 `NULL` 로 남으면 PDA 에서 그 부품의 위치가 안 잡힌다. PDA 위치 이동(`WhEndpoints`)은 `SP_EXTRA` 밖으로 옮기면 `ExtraLocation` 을 지운다. 이 마이그레이션 없이 신 Web 을 올리면 MD-026 목록·저장이 매번 예외다(`Invalid column name 'ExtraLocation'`).
