**PP-002 수주 자동 확정**(10-13 사용자 결정): 카드 헤더의 「자동 확정」 스위치(승인 권한 A — 수주 확정과 같은 권한, 없으면 상태만 보이는 비활성)가 `SYS_Config.PP_SO_AUTO_CONFIRM`(bool `true`/`false`, 기본 `false`, SYS-009 PP 에도 보임)을 켜고 끈다. 켜져 있으면 **세 유입 경로 전부**(엑셀 업로드·「API 가져오기」·AMES.Api PO Sync 워커)의 **신규** 수주가 Open 을 거치지 않고 저장 시점에 Confirmed 가 된다 — 세 경로가 모두 `PpRepository.UpsertCustomerOrders` 를 타고 그 메서드가 같은 트랜잭션에서 플래그를 읽으므로 호출자 코드는 플래그를 모른다(기존 행 갱신은 상태 유지). 켤 때는 확인창 뒤 **플래그 ON + 그 시점의 Open 수주 전부 확정을 한 트랜잭션**(`EnableSoAutoConfirm`, 「아니오」면 아무것도 바꾸지 않음, Open 0건이면 확인창 없음), 끄기는 플래그만(`DisableSoAutoConfirm`, 이미 확정된 건 그대로). 감사 `PP-002/AUTOCONFIRM_ON`(확정 건수)·`AUTOCONFIRM_OFF`(만들 때 `ActionType` 이 varchar(15)라 밑줄 하나 — 10-15 varchar(20) 으로 넓혔어도 지난 감사 행과 맞추려고 코드는 그대로). 규칙 정본 `AMES.Data.Services.SoAutoConfirm`(행 없음·비활성 = 꺼짐, 테스트 `SoAutoConfirmTests`·DB `SoAutoConfirmRepositoryTests`(`AMES_TEST_CONN` 지정 시, SYS_Config 행·다른 Open 수주를 끝에 원상 복구)). 기본 행은 `dist/migrate_pp_so_auto_confirm.sql`(순서 무관·재실행 안전, 10-13 개발 DB 적용, `rebuild_db.sh`)이 만들지만 화면에서 켜면 없어도 만들어 쓴다. **워커 경로가 플래그를 따르려면 신 `AMES.Data` 가 든 AMES.Api 도 다시 게시해야 한다**(구 Api 는 계속 Open 으로 넣는다). 자동 확정된 수주는 PP-003·APS 의 Confirmed 수요에 바로 잡히며, 수량·납기 변경이 사람 확인 없이 확정 수요가 되는 점은 PO Sync 의 정합성 한계(아래)와 같이 유념.

**PP-002 오더 선택·미등록 품번**(11-18 사용자 결정): 평소엔 체크박스 열이 없고, 「오더 선택」 버튼을 누르면 체크박스가 생기며 같은 버튼이 「확정 (n)」으로 바뀐다(옆에 「취소」). 머리글 체크는 **지금 보이는 페이지의 행만** 고르고(전체 `_view` 아님) 다른 페이지에서 고른 행은 유지된다. 품목 마스터에 없는 품번(「미등록」 배지)은 **확정 불가** — 체크박스·행별 「확정」 버튼 비활성, 서버(`ConfirmCustomerOrder`·`EnableSoAutoConfirm`·`CountOpenCustomerOrders`·`UpsertCustomerOrders` 자동 확정 INSERT)도 `MD_Item` 존재를 조건으로 걸어 Open 으로 남긴다(등록 뒤 수동 확정). 필터 줄 「미등록 제외」 체크로 미등록 행을 목록에서 뺄 수 있고, 맨 왼쪽 고정 열은 페이지를 이어 세는 순번(No.). **확정 취소**(11-18): 잘못 확정한 수주는 `RevertCustomerOrder` 로 Confirmed → Open 되돌린다 — 행별 「확정 취소」 버튼 또는 오더 선택 모드의 「확정 취소 (n)」, 확인창 뒤 감사 `PP-002/REVERT`. **활성 WO(취소 제외)가 있으면 서버가 거부**(WO 를 먼저 취소해야 함), 체크박스도 Open·등록 건(확정용)과 WO 없는 Confirmed 건(취소용)만 켜진다.

##### APS 생산계획 (PP-APS) — `Pp/ApsPlan.razor`, `/pp/aps-plan`

SEG APS(Seoyon E-Hwa Georgia 생산계획 웹앱, 재구축본 `Seg.Aps.Server`)의 순수 계산 엔진을 `AMES.Data.Aps` 로 이식한 것이다. **완제품 공급 자동계산 → 사출 소요 전개 → shot 환산 → 사출기 주야 배분 → 부하율·부족 신호등**을 내고, 저장된 실행에서 WO·라인 슬롯을 만들어 POP 까지 잇는다. PP-003 과는 대체가 아니라 앞뒤 관계다 — APS 가 만든 WO 도 PP-003 의 기발행 수량에 잡히고, PP-003 이 먼저 만든 WO 슬롯은 APS 화면에 잠긴 칸(회색 자물쇠)으로 들어온다. **완제품 품번으로 잡힌 사출 라인 슬롯**(코어 품번 WO 모델 — WO 는 완제품 품번이고 INJ 단계 슬롯도 그 품번)은 그 완제품의 **BOM 사출 자식 등록 계획**으로 읽는다: 자식의 사출 라인에 있는 부모 슬롯 수량 × 간선 QtyPer(스크랩 포함)를 자식마다 잠긴 칸에 더하고 부하에도 넣는다(10-02 사용자 결정 4-(a), `ApsRepository.ParentSlotsFor`, 정본 `ApsRepositoryTests.Parent_item_slot_…`). 부모가 자기 금형으로 직접 찍히는 품번(같은 품번 규칙)이면 그 슬롯은 부모 자신의 것이고, 자식 사출 라인이 아닌 라인의 부모 슬롯은 종전대로 "계획 라인이 아니라" 경고다.

MC 는 창(주간 → 야간)마다 교체시간 + 1분(교체 뒤 생산 1분 이상)이 한 빈틈에 들어가는 첫 자리에 두며, 어느 창에도 그런 자리가 없으면 **수량 있는 첫 창의 첫 틈(틈이 없으면 그 교대 밴드 시작, 그것도 없으면 하루 시작) 앞에 MC 를 억지로 두고 그 뒤 남은 틈에 초과로 싣는다**(10-08 — 종전에는 MC 도 생산 슬롯도 쓰지 않고 그 날 전량 Shortfall 이었다; 억지 MC 는 휴게·점유 구간과 겹칠 수 있고 끝은 1440 으로 자른다). MC 가 들어간 창보다 앞 창의 수량은 금형이 안 바뀐 창이라 그 교대 밴드 시작의 0분 슬롯에 초과로 남는다. PP-LSB 「적용」(`LineScheduleRepository.SaveSchedule`)은 그 날의 APS 형제 0분 행(`EntryType='WO'`·`WoID` 있음·`EndMin ≤ StartMin`·수량 > 0)을 지우기 전에 읽어 되살린다 — 보드는 0분 행을 싣지 않으므로, 보드가 그 WO 에 실제 슬롯을 준 경우에만 그 슬롯이 0분 행을 대신한다(되살린 행이 있으면 placeholder 행은 쓰지 않는다). **「적용」·「초기화」는 보드를 연 시점의 행 지문(`LineScheduleRepository.VersionOf`)을 DB 의 현재 행과 비교해 다르면 아무것도 바꾸지 않고 거부한다**(10-10 — 전에는 라인·날짜 행을 전부 지우고 보드 값만 다시 넣어, 보드를 연 사이 PP-003·APS·다른 보드가 넣은 슬롯이 조용히 미배치로 돌아갔다): 화면은 `ScheduleChangedException` 을 받아 안내 + 「다시 불러오기」(미저장 편집은 버림)를 보인다. 확인한 행은 UPDLOCK 으로 잡고 그 행 ID 만 지우며(확인 뒤 PP-003·APS 가 넣은 행은 남는다), 보드끼리는 `sp_getapplock`(라인·날짜)으로 줄을 세운다. 정본 테스트 `LineScheduleConcurrencyTests`. BOM 규칙 자식의 재고도 같은 통합재고 규칙(`WH_Inventory` `PartNo` 별 `SUM(Qty)`, `Qty > 0`, 위치 무관)이며, PP-APS 는 **통합재고 마이그레이션**(`dev`·`pop` 의 `migrate_unify_inventory.sql`·`migrate_fg_inventory_consolidation.sql`·`migrate_fg_shipment_consolidation.sql`)이 적용된 DB 를 전제한다 — 구 형상(`FG_Inventory`·`WH_Inventory.OnHandQty`)에서는 조회가 `Invalid object name`/`Invalid column name` 으로 실패한다. 수량 0으로 덮인 행(`SkippedExisting`)은 `WoID` 가 남지 않아 같은 실행을 다시 「WO 생성」하면 대상에 다시 보인다(재생성은 아니다 — 이미 있는 슬롯 수량만큼 다시 빼므로 이중 발행은 없다). 저장 없이 화면을 편집한 뒤 「WO 생성」하면 저장본(마지막 「저장」) 기준으로 만들어진다(확인창이 안내).

## LOT 작업지시 이동 (PP-LOT, 11-18)

POP 은 확정 때 라인·품번이 같은 열린 단계(Released·In Progress) 중 빠른 WO(진행 중 → 우선순위 → 납기)에 LOT 을 자동으로 붙인다(`SP_POP_INJ_ConfirmByLotCode_GetWorkOrderRouting`). 엉뚱한 WO 에 붙은 LOT 은 **LOT 조회(`pp/lot`)에서 체크박스로 골라 「작업지시 이동」** 으로 옮긴다(편집 E 권한 — `migrate_pp_lot_screen.sql` 이 PermissionCriteria `_XX`→`__X`, Admin `RXX`→`REX`). `WorkOrderRepository.MoveLots`(한 트랜잭션, 하나라도 거부되면 전부 되돌림) — 같은 공정·라인·품번 LOT 만 함께, 확정(CONFIRMED) LOT 만. 받는 WO 는 같은 공정·라인·품번의 열린 단계가 있는 종결 아닌 WO(`ListLotMoveTargets`), 또는 「작업지시에서 해제」(WoID NULL = 재고). `tbl_Lot`·`PR_ProductionResult`·`PR_DefectDetail` 의 WoID 를 바꾸고 원래 단계 CompletedQty 에서 양품을 빼고(끝난 WO 는 수량만 줄이고 상태·종료는 그대로) 새 단계에 더한다(`BumpStepCompleted`). 팔레트·창고 재고는 건드리지 않는다. 감사 `PP-LOT`/`MOVE_WO`. 정본 `LotMoveDbTests`(AMES_DEV).

**수량·순번 이동(11-18 추가)**: 팝업은 고른 LOT 이 속한 작업지시(재고 포함)의 확정 LOT 을 「작업지시 · 공정 · 라인 · 품번」 묶음(`ListLotMoveGroups`)으로 보여 주고, 받을 작업지시(원래 WO 는 후보에서 제외)와 **수량**·시작 LOT 번호를 입력하면 LOT 번호 순번(`ListLotMoveSequence` — 번호 길이 → 번호순)대로 그 수량만큼 옮긴다(이동 대상 범위를 미리 보여 줌). 품목이 다른 WO 는 후보에 없고 서버도 `ItemMismatch` 로 거부하며, 공정·라인이 다르면 `NoTargetStep` 으로 거부한다.

### 워크스테이션별 실적 (StationCode, 11-18)

- POP 은 로그인 때 라인 → **스테이션(워크스테이션)** 을 고르고 그 코드가 세션 `PR_PopSession.TerminalID` 로 들어간다. 실적 INSERT SP 5개(`SP_POP_{INJ,IMG,PNT}_ConfirmByLotCode_InsProductionResult`·`SP_POP_LOT_ReverseConfirmedResult_…`·`SP_POP_RWK_Rework_…`)가 세션 TerminalID 를 **`PR_ProductionResult.StationCode`** 로 같이 쓴다(SP 시그니처 변경 없음 — 구 바이너리 호환). 마이그레이션 `dist/migrate_result_station.sql`(기존 실적은 세션 TerminalID 로 채움, 없으면 NULL).
- WO 흐름(WoFlowGraph)의 공정 단계 노드는 라인 줄 아래에 스테이션별 양품 수량(`ListStepStations`)을 보인다. 스테이션 미기록 실적(이전·PDA·웹)은 `—` 한 줄, 미기록뿐이면 줄을 더하지 않는다. WO 라우팅·슬롯은 라인 단위 그대로.
- **확장(11-18, `dist/migrate_station_extend.sql`)**: `tbl_Lot.StationCode`(LOT 을 만든 스테이션 — 원천 LOT 발행 SP 3개가 발행 사번의 열린 POP 세션 스테이션(`FN_POP_OpenStation`)을 쓰고, 비어 있으면 확정(스캔) SP 의 세션 스테이션으로 채운다), `PR_DefectDetail.StationCode`(그 실적 → 없으면 LOT 의 스테이션), `MD_Equipment.StationCode`(설비가 속한 스테이션), `PP_EquipSignal`·`PR_EquipStatusLog`·`PR_InjCondLog.StationCode`. LOT 조회·LOT 상세의 스테이션은 저장된 실적 `StationCode` 를 먼저 쓴다. 테스트 `StationRecordingDbTests`.
- **PLC 준비(아직 연결 전)**: 신호를 쓰는 곳(`OeeRepository.SetEquipSignal`·`InjCondRepository.InsertLog` 의 `stationCode` 선택 인자, `SP_POP_EQUIP_LogStatus`)은 스테이션을 알면 그것을, 모르면 **설비 마스터의 `StationCode` → 라인에 스테이션이 하나뿐이면 그 코드(`FN_StationOfLine`)** 순으로 채운다. 라인에 스테이션이 여럿이면 NULL 이다 — PLC 가 붙으면 `MD_Equipment.StationCode` 만 맞추면(또는 브리지가 `stationCode` 를 넘기면) 코드 변경 없이 스테이션별로 쌓인다. InjAgent 가 만드는 LOT 은 사번이 `AGENT` 라 세션이 없어 NULL 이다.
- 스캔한 실적은 DB 에 바로 들어가므로 WO 팝업의 흐름 보기(자동 새로고침)에 스테이션별 수량이 실시간으로 나타난다.

**PP-003 WO 생성 불가 사유 표시**(11-20 사용자 요청): Status 열이 「라우팅 미지정」 한 줄 대신 **막힌 이유를 전부** 보인다 — 품목 마스터 없음·라우팅 미지정·코어 품번 불명(BOM)·LOT PREFIX 없는 라인·생산 라인 없음(BOP)·금형 미등록. 서버가 거부하는 규칙(`RejectNoCore`·`RejectNoLotPrefix`·`RejectNoMold`)과 같은 판정을 `AMES.Web.Services.WoBlockers.Diagnose`(읽기 전용)가 조회 때 수주마다 미리 계산하고(같은 품번·라우팅은 1회), 이유를 누르면 고치는 화면이 **새 탭**으로 열린다: 품목·라우팅 → `/md/fd/items?q=품번`, 코어 → `/md/fd/bom?q=품번`, LOT PREFIX → `/md/rp/line?q=라인`, 생산 라인 → `/md/rp/bop?q=품번`, 금형 → `/md/re/mold`(금형 화면은 품번 검색이 없어 이동만). 이 네 화면(Items·Bom·Bop·Line)은 `?q=` 로 검색칸을 미리 채운다. 이유가 있는 수주는 체크·일괄 생성에서 빠지고 상단 「막힘」 KPI 에 센다. 문구는 resx `PP.PlanConfirm.Why.*`.
