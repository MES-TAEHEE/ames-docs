### AMES.Pop — 공장 터미널 (WinForms + Blazor Hybrid)

터미널은 로그인 시 선택한 라인의 WC ProcessCode 로 모듈 자동 분기.

대시보드(INJ-02)·작업지시 접수(INJ-03)·금형 교체(INJ-06)·생산 현황(INJ-07)은 미사용으로 삭제됨 (화면·팝업·레거시 WinForms 폼 포함).
구 단독 화면(`/inj02`~`/inj08` 라우트)도 모두 삭제됨 — INJ 는 INJ-MAIN(+ 수동 라벨 생성 버튼) + 팝업(불량·안돈)만 남는다. 팝업 공통 셸은 `Pages/InjPopups/PopupShell.razor`.
좌측 품번 목록은 `MD_Bop.StationCode` = 세션 스테이션(`PopSessionDto.TerminalId`) 기준이고, 좌측 수치는 `InjLotRepository.GetDailyItemSummary(line, station, date)` — 우측 「오늘 스캔 이력」은 터미널 파일(`scan-history.bin`, `Services/ScanHistoryStore`)에 라인·전기일별 최근 50건으로 남아 다시 열거나 다시 로그인해도 이어지고 전기일이 바뀌면 비워진다(10-29 INJ-MAIN-TC-019). 금형 칩은 사출 샷 현황판과 같은 규칙 — 사출기 장착 금형 → 최근 사출 LOT 금형(`SP_POP_MOLD_GetLineMoldId`), 둘 다 없을 때만 작업지시 금형(10-29 E2E-TC-013). 우측 칩은 좌측 날짜와 무관하게 금일 수치이고, 스캔 확정에 성공하면 좌측도 금일로 돌아간다. LOT 생성일 기준으로 `INPUT = FINAL + NG + 미확정` 이 성립한다. 전부 LOT 상태로 센다 — FINAL = CONFIRMED, NG = NG_BLOCKED + DEFECT + SCRAPPED (IMG 는 DEFECT + SCRAPPED), 미확정 = RAW. PR_DefectDetail 은 집계에 쓰지 않는다. INJ 단계의 생산 품번은 **BOM 의 코어**(`AMES.Data.Services.CoreItemResolver.ReadByInjFlag` — 10-14 부터 웹 WO 발행(PP-003·PP-004·PP-APS WO 생성)은 PP-APS BOM 규칙과 같은 **InjFlag 기준**: 유효 BOM 을 다단계로 내려가 `MD_Item.InjFlag = 1` 인 사출품에서 멈추고 InjFlag 0 인 서브조립은 더 내려가며 MATERIAL 은 내려가지 않는다(깊이 상한 `ApsRepository.BomWalkMaxDepth`). 사출품 1개면 그것 — 레일만 있는 품번도 레일, 여럿이면 그중 품명이 `CORE` 로 시작하는 것이 정확히 1개일 때 그것(코어 + 레일 — 단계 품번 칸이 하나라 코어를 고른다, 사용자 결정), 그 밖은 PP-003 이 `NoCore` 로 거부, MATERIAL 아닌 자식이 없으면 WO 품번 그대로. 개발 DB 완제품 77개는 품명 규칙과 같은 코어로 풀린다 — 정본 테스트 `CoreItemResolverTests.ByInjFlag_*`·`CoreItemDbTests.ReadByInjFlag_*`. POP IMG 코어 스캔 검사(`ImgLotRepository.CreateFromCore`)는 아직 품명 규칙 `CoreItemResolver.Read` 이고 POP 담당이 옮긴다)이며 WO 발행 때 `PP_WorkOrderRouting.ItemNo` 에 스냅샷된다(`dist/migrate_wo_step_item.sql`). INJ 스테이션 BOP·금형 매핑·LOT 품번은 코어이고 WO 품번은 완제품이다. 열린 WO 해석은 전부 `COALESCE(r.ItemNo, w.ItemNo)`(`WorkOrderRepository.OpenStepForItemFilter`)이고 **헤더가 끝난 WO(완료·입고·마감·취소, `WoStatusRules`)는 단계가 열려 있어도 받지 않는다**(10-27 — C# `OpenStepWhere` 와 SP 사본 모두), INJ-MAIN 의 PLAN 도 단계 품번으로 센다. 수동 라벨은 좌측 선택 품번(열린 WO 가 있으면 `WorkOrderDto.StepItemNo`)으로 LOT 을 만든다. **열린 WO 가 없어도 생산은 막히지 않는다**(10-01 사용자 결정) — 스캔 확정은 `PR_ProductionResult`·`tbl_Lot` 의 `WoID` 를 NULL 로 남기고 단계 반영(`BumpStepCompleted`)만 없다. 보고서는 WO 를 LEFT JOIN 하므로 그대로 집계되고, 불량 역분개·재작업도 WoID NULL 로 따라간다. 좌측 `WO 없음` 배지는 안내일 뿐 막지 않는다. dev DB 는 `dist/seed_md_bop_inj_dev.sql` 로 ST-INJ-01 BOP 를 채운다.
INJ 는 `AcceptWo` 를 부르지 않으므로 `BumpStepCompleted` 가 첫 실적에서 단계·헤더를 `Released → In Progress` 로 올리고 `ActualStart` 를 찍는다. `TerminalLock` 은 INJ 에서 기록하지 않는다(IMG 는 `AcceptWo` 그대로).

구 단독 화면(IMG-02~07, `/img02`~`/img07`)은 모두 삭제됨 (화면·도움말·레거시 WinForms 폼·전용 CSS 포함) — IMG 는 IMG-MAIN + 팝업(불량·안돈)만 남는다.
IMG 도 INJ 와 같은 LOT 모델(1 LOT = 1 EA, RAW → CONFIRMED)을 쓰되 테이블은 별도 `PR_ImgLot`(`dist/migrate_img_lot.sql`)이고 리포지토리는 `ImgLotRepository` 다. 에이전트가 없으므로 LOT 은 **사출 Core 스캔**이 만든다(`ImgLotRepository.CreateFromCore`): Core(INJ LOT)는 `CONFIRMED` 만 받고(규칙 정본 `AMES.Data.Services.CoreLotRules`, 테스트 `CoreLotRulesTests`) 한 번만 쓸 수 있으며, 완제품 품번 = 그 코어를 INJ 단계 품번으로 갖는 **IMG 라인의 열린 WO 품번**(`WorkOrderRepository.OpenStepByCoreFilter`, 라우팅 A = INJ → IMG — 코어 품번이 아니다), 연결은 완제품 `tbl_Lot.ParentLotID` = Core LotID 다. 그런 WO 가 없으면 **좌측에서 고른 완제품 품번으로 WO 없이 만든다**(10-01 사용자 결정 — 선택 품번의 유효 BOM 코어(`CoreItemResolver`)가 스캔 코어와 다르면 `CoreMismatch`, 선택이 없거나 마스터에 없는 품번이면 `NoFinishedItem`, 둘 다 반환 품번은 코어; BOM 이 코어를 못 정하는 품번은 선택을 믿는다). PGN·ALC·MountPos 는 완제품 품번, 수주처는 그 WO 로 읽는다(WO 없으면 NULL — 라벨 V 토큰이 빈다). 판정 OK(IMG·PNT)의 WO 해석은 **라벨에 찍힌 수주처와 같은 수주의 열린 WO 를 먼저** 고른다(10-28 — 발행 뒤 우선순위가 바뀌어도 라벨과 실적의 WO 가 갈리지 않게, `SP_POP_IMG/PNT_ConfirmByLotCode_GetWorkOrderRouting @Cust`). 판정 OK 도 WO 없이 확정된다(`WoID` NULL, 단계 반영 없음). 예외용 라벨 발행 버튼도 좌측 선택 품번만 있으면 된다. 생성 즉시 `LabelPrinter.Print(ImgLotDto, shift)` 로 동기 출력하고 OK/NG 판정 팝업을 띄운다 — OK = `ConfirmByLotCode`, NG = 불량코드 터치 → `RegisterDefect`(DEFECT → REWORK). 판정 없이 닫은 LOT 은 RAW 로 남고(오늘 LOT 목록의 「발행 취소」로 지울 수 있다 — 10-27 `ImgLotRepository.VoidRawLot`: RAW 만, LOT 행 삭제·LotNo 결번, 코어 재고를 낱개 행으로 되살리고 IN 거래 `IMG_VOID`, 같은 코어 재스캔 가능, 오프라인에서는 숨김) 완제품 라벨을 다시 스캔하면 팝업이 다시 뜬다(RAW 라벨 스캔은 더 이상 바로 확정하지 않는다). 예외용 **라벨 발행** 버튼(`CreateRawLot`)은 Core 없이 발행하며 같은 팝업을 띄운다. `LabelDispatcher` 는 INJ 세션에서만 돌아 이중 발행이 없다. DB 통합 테스트는 `AMES.Data.Tests/ImgLotRepositoryTests`(AMES_DEV 필요).
IMG 라벨은 INJ 양식이 아니라 **완제품 고객 표준 라벨**(`AMES.Devices.ImgLabelBuilder`)이다: 좌측 DataMatrix = `[)>RS06GSV{수주처}GSP{품번,하이픈제거}GSS{PGN+ALC}GST{yyMMdd}{part4M}{LotNo}GSEGSC:RSEOT`(`^FH_` 16진 이스케이프), 우측 글자 = ALC(대)·장착위치·발행일·품번·LotNo. part4M = `1` + 하이픈 뺀 품번 6·7번째 글자 + 교대 글자(DAY=A·NIGHT=B·그 외 C, `LabelPrinter.ShiftLetter`). 수주처 코드는 발행 시점 열린 WO → `PP_CustomerOrder.SoID` → `MD_Customer.CustomerCode` 로 정해 `PR_ImgLot.CustomerCode` 에 박아 둔다(재출력 불변). PGN·ALC 는 `MD_Item`, 장착위치는 `MD_Item.MountPos`(`dist/migrate_md_item_mount_pos.sql`, FL/FR/RL/RR). 샘플 라벨 우측 하단 'D' 칸은 정의 전이라 비워 둔다.
스캐너는 DataMatrix 문자열 전체를 보내므로 `ImgScanParser.ExtractLotCode` 가 T 토큰 끝 9자를 LotNo 로 뽑는다 — 시리얼(제어문자 보존)·HID 웨지(제어문자 소실)·단순 LotNo 라벨 모두 처리하며 단위 테스트(`AMES.Pop.Tests/ImgScanParserTests`)가 정본이다. 발행은 실적이 아니며 판정 OK 가 `ConfirmByLotCode` 로 한 트랜잭션으로 열린 WO 해석 → PR_ProductionResult 1 EA → LOT CONFIRMED + `BumpStepCompleted` 를 처리한다. 원단 롤·본딩은 다루지 않는다(차감·롤 ID·본딩 사이클 로그·`BondSetupID` 기록과 화면 칩 모두 없음).
좌측 수치는 `ImgLotRepository.GetDailyItemSummary(line, station, date)` — 우측 칩은 좌측 날짜와 무관하게 금일 수치이고, 스캔 확정에 성공하면 좌측도 금일로 돌아간다. INJ 판과 같이 LOT 생성일 기준으로 `INPUT = FINAL + NG + 미확정` 이 성립한다. 우측 목록은 `GetTodayLots`(오늘 발행 LOT 전부, 최신순). dev DB 는 `dist/seed_md_bop_img_dev.sql` 로 ST-IMG-01 스테이션·데모 품번·BOP 를 채운다 (IMG 라인은 스키마에 스테이션이 없어 이 시드 없이는 로그인 자체가 안 된다).
**BOM 자동 차감(backflush, 10-15 사용자 결정)**: LOT 이 **처음 CONFIRMED 가 되는 순간**(INJ 스캔 확정·IMG 판정 OK·확정된 적 없는 LOT 의 재작업 수리 양품) 같은 트랜잭션에서 `BackflushRepository.Apply` 가 그 LOT 품번의 유효 BOM(APPROVED·기간 내, 코어 해석과 같은 선택) **직접 자식 중 `ItemType='MATERIAL'`**(IMG 는 10-27 부터 사출품 자식 `InjFlag = 1` 도 — 스캔한 코어 품번만 빼고(`ConsumeCore` 가 이미 지움) 레일 등을 뺀다, `BackflushRules.IncludesInjection` = PNT·IMG) 을 `QtyPer × (1 + ScrapPct/100)` 만큼 **그 라인(`MD_Line.LotPrefix` 위치)의 라인 재고**(`WH_Inventory`)에서 입고일 FIFO 로 뺀다(SUB 자식 = 코어는 `ParentLotID` 로 이어져 제외, 단위는 BOM UOM = 품목 기본 단위). 모자라면 라인×품번 자리표시 LOT `BF-{LotPrefix}-{품번}`(UnitType PART)을 만들어 **음수로 내리고**, 뒤에 실물 LOT 이 올라오면 다음 차감 때 그 LOT 에서 자리표시를 먼저 메운다(`ADJ`/`BACKFLUSH_NET` 두 행). 거래는 `WH_InventoryTransaction` `OUT`/`BACKFLUSH`, `SourceID = tbl_Lot.LotID`(멱등 판정, 새 컬럼 없음), `Note = "{LotCode} {품번}"` — 행마다 `LotNo` 가 차감한 자재 LOT 이라 완제품 LOT ↔ 자재 LOT 을 이 표로 잇는다(투입 스캔이 아닌 FIFO 장부상 LOT). **자리표시를 실물 LOT 으로 메우는 `BACKFLUSH_NET` 두 행은 부족을 만든 원래 LOT 을 `SourceID` 로 쓴다**(10-28 사용자 결정, `BackflushRules.AssignNetOwners` — 자리표시에서 뺀 양 − 이미 메운 양이 남은 LOT 을 오래된 순으로, 합이 지금 자리표시 음수보다 크면(옛 행은 메운 LOT 쪽에 기록) 그 차이는 오래된 LOT 부터 메워진 것으로 보고, 주인을 모르는 양은 지금 확정 LOT, 메모 `(by {메운 LOT})`). **자재 LOT 추적의 단일 기준은 뷰 `dbo.VW_MaterialLotUsage`**(`migrate_pop_stored_procedures.sql` — 완제품 LotID·자재 품번·자재 LOT·사용량·위치·시각·`Basis` LEDGER/UNRESOLVED(자리표시에 남은, 실물 LOT 을 아직 모르는 양)) — 자재 투입 스캔을 만들면 이 뷰만 그 기록으로 바꾸거나 UNION 한다. LotPrefix 없는 라인(LINE-RWK-01 등)은 차감 없이 오류로만 남는다 — 재작업은 LOT 의 원래 라인에서 뺀다. 정본 `AMES.Data.Services.BackflushRules`(`BackflushRulesTests`), DB `BackflushRepositoryTests`(롤백 트랜잭션 안에서 CHECK 완화까지 스스로 적용)·`BackflushConfirmTests`(`AMES_TEST_CONN` 지정 시, 같은 직렬 컬렉션).
**OK 제품 팔레트 적재 → `WH_Inventory`(10-21 사용자 결정, INJ·IMG 공통)**: 스캔칸에 **팔레트 바코드(`EOS-PLT-` 로 시작 — MD-034 발행 번호 `EOS-PLT-yyMM-nnnn`)를 먼저 찍어** 그 터미널의 「현재 팔레트」로 삼고(`PalletStockRepository.Inspect`, 칩 `팔레트 EOS-PLT-2610-0002 · 3 / 24`), 그 뒤 LOT 스캔 확정(INJ)·판정 OK(IMG)가 **같은 트랜잭션에서 `PalletStockRepository.Load`** 로 제품을 그 팔레트에 싣는다 — WH_Inventory 의 팔레트 묶음 규칙(SCM 케이스·PDA 출고와 같음) 그대로: 머리 행(LotNo = 팔레트 번호, UnitType `PALLET`, Qty 0, 없을 때만 생성) 아래 제품 행(LotNo = LotCode, UnitType `PART`, Qty 1, PartNo = LOT 품번(INJ 는 코어·IMG 는 완제품), `ParentLotNo` = `PalletNo` = 팔레트 번호, **`LocationNo` NULL = 미배정** — PDA FG 입고(Fg01)가 "재고 행은 있고 위치가 빈" LOT 을 위치 배정(MOVE)으로 처리하므로 그대로 이어진다) + `WH_InventoryTransaction` IN(`SourceType='PROD_CONFIRM'`, `SourceID = tbl_Lot.LotID`). 적재 판정 정본 `AMES.Data.Services.PalletLoadRules`(테스트 `PalletLoadRulesTests`): MD_Pallet 에 있고 `ActiveFlag` 1·`ShippedFlag` 0 이어야 하고, **한 팔레트에는 한 품번 — 단 같은 활성 금형·색상(`MD_MoldItem` MoldID × Color, APS 형제 기준과 같음)의 형제 품번(LH/RH)은 함께 실을 수 있다**(10-21 사용자 결정 — 복제본 활성 금형×색상 31개 중 25개가 LH/RH 품번이 다른 2캐비티 쌍이라 한 품번 규칙이면 샷마다 혼적 거부에 걸린다; 형제가 아닌 품번이 실려 있으면 `Mixed`), **적입수량은 품번마다 따로 센다**(그 팔레트 자식 행 중 Qty > 0 을 품번별로 센 수 ≥ 그 품번 `MD_Item.PalletQty` 면 `Full` — APS 가 사출 품번마다 자기 PalletQty 를 포장 단위로 계획·WO 를 올림하므로 「계획 1포장 = 팔레트 1개」가 유지된다; LH/RH 쌍 팔레트의 PalletQty 는 "그 품번이 쌍 팔레트에 실리는 개수"로 넣는다) — 적입수량이 없는 품번(NULL·0)은 생산을 막지 않게 제한 없음. 칩은 한 품번만 실렸으면 `3 / 24`, 형제가 같이 실렸으면 `D0111-PI010 12 · D0121-PI010 11 / 24`(고른 품번 먼저, 적입수량은 고른 품번 것, 없으면 `—`)이고 고른 품번이 가득 차면 빨강. 판정은 확정 트랜잭션 안에서 MD_Pallet 행을 `UPDLOCK, HOLDLOCK` 으로 잡고 하므로 두 터미널이 같은 팔레트에 동시에 실어도 넘치지 않는다. **못 실으면 확정도 되지 않는다**(`InjConfirmOutcome`·`ImgConfirmOutcome` 의 `PalletNotFound`·`PalletUnavailable`·`PalletMixed`·`PalletFull` — LOT 은 RAW 로 남고 실적·차감도 없다; 확정됐는데 팔레트에 없는 제품이 생기지 않게). 팔레트 없이 LOT 을 찍으면 「팔레트를 먼저 스캔하세요」, 가득 차면 「새 팔레트를 스캔하세요」(IMG 는 코어 스캔·라벨 스캔 모두 그 자리에서 막고, 예외용 라벨 발행 버튼으로 연 판정 팝업의 OK 도 팔레트가 없으면 거부). 출고(PDA FG OUT)가 자식 행을 0 으로 내리므로 회수된 팔레트는 다시 쓸 수 있다. **IMG 가 코어를 스캔해 완제품 LOT 을 만드는 순간 그 코어의 재고 행은 **지우고**(10-22 사용자 결정 — 0 으로 남기지 않는다, 이력은 거래 테이블) OUT(`SourceType='IMG_CORE'`, `SourceID` = 완제품 LotID, QtyBefore 1 → QtyAfter 0)만 남긴다**(`PalletStockRepository.ConsumeCore` — 코어가 팔레트에 남은 것처럼 APS 가용재고에 잡히지 않게; 재고 행이 없는 옛 코어는 아무것도 안 함, 수량 0 으로 남아 있던 옛 행은 거래 없이 지움). 리포지토리의 `ConfirmByLotCode(…, palletNo, out backflush)` 는 **palletNo 가 null 이면 종전대로 재고 없이 확정**한다(기존 테스트·다른 호출자 — POP 화면이 팔레트를 강제한다). 현재 팔레트는 화면 메모리뿐이라 재로그인·재시작하면 다시 스캔한다. 재작업 수리 양품 중 활성 ASSY는 팔레트 스캔 없이 위치 미배정 PART 재고 1 EA로 복구한다(10-29 사용자 결정). **불량 등록은 팔레트에서 내린다**(10-22): INJ·IMG·PNT 라인 불량 팝업의 `RegisterDefect` 가 같은 트랜잭션에서 `PalletStockRepository.Unload` 로 그 LOT 의 재고 행(LotNo = LotCode, 팔레트 머리 행 제외)을 **지우고** OUT 거래(`SourceType='POP_DEFECT'`, `SourceID = tbl_Lot.LotID`, QtyBefore 1 → 0, Note `{LotCode} {품번} DEFECT {불량코드} ← {팔레트}`)만 남긴다 — `ConsumeCore` 와 같은 규칙(0 으로 남기지 않는다)이라 불량품이 팔레트 적재 수(Full 판정)·PDA 팔레트 출고·APS 가용재고에 남지 않는다. 실린 적 없는 LOT(RAW·NG_BLOCKED, 팔레트 없이 확정된 옛 LOT)은 행이 없어 아무것도 하지 않는다. 재작업 스테이션 폐기(`ReworkRepository.Scrap`)도 같은 처리를 `POP_SCRAP` 으로 하되 불량 등록이 이미 뺀 LOT 이라 보통은 할 일이 없는 **안전망**이다(이 기능 전에 등록돼 행이 남은 LOT 만 실제로 지운다). 이미 PDA FG 입고로 위치를 받은 행도 지운다(물건이 라인으로 돌아왔으니 창고 재고에서도 빠져야 한다) — 그때는 결과 `PalletUnloadResult.LocationNo` 가 있어 불량 팝업 배너·재작업 토스트가 「입고된 재고(위치 X)에서 뺐습니다 — 창고에 알리세요」(키 `DfStockRemovedLocated`·`RwkStockRemovedLocated`)를 보인다. 수리 양품(DEFECT → CONFIRMED)의 활성 ASSY 재고 복구는 같은 판정 트랜잭션의 `PalletStockRepository.RestoreReworkedAssy`가 담당한다. 팔레트에는 자동 재적재하지 않고 위치 미지정 재고와 IN `PROD_REWORK` 거래를 만든다. 정본 테스트 `PalletLoadDbTests.Defect_registration_takes_the_lot_off_its_pallet_and_scrap_is_the_safety_net`(`AMES_TEST_CONN` 지정 시, 10-22 개발 DB 통과). 새 테이블·컬럼 없음. LOT 상태 기계(`PR_InjLot`·`PR_ImgLot.ConfirmStatus`, 정본 `AMES.Data.Services.LotDefectRules`): `RAW → CONFIRMED`(스캔), `RAW/CONFIRMED/NG_BLOCKED → DEFECT`(라인 불량 팝업), `DEFECT → CONFIRMED`(수리) / `→ SCRAPPED`(폐기). `NG_CONFIRMED` 는 폐지됐다. 스캔 확정 **뒤에** 늦게 온 취출 로봇 NG 는 InjAgent 설정 `Agent:LateNgDefectCode`(기본 `INJ-D08` 로봇 NG — `dist/seed_defect_robot_ng.sql`, 10-28)로 불량 등록되고(실적 역분개·재작업 대기열), 설정을 비우면 경고 로그만 남는다(`InjLotRepository.MarkNgBlocked`).
**`RAW` 의 뜻**(11-17): LOT 이 막 만들어져 번호·라벨은 나왔지만 **아직 스캔(판정)으로 확정하지 않은 미확정 상태**다. 사출은 기계가 샷마다 RAW LOT 을 쌓고, 감싸기·도장은 라벨을 발행하면 RAW 이며 판정 OK(확정)해야 CONFIRMED 가 된다(판정 없이 닫으면 RAW 로 남는다). RAW LOT 은 **작업지시(`tbl_Lot.WoID`)에 아직 묶이지 않고 실적·자재 자동 차감도 없으며 양품이 0** 이다 — 확정 때 같은 트랜잭션에서 실적 1 EA·WO 연결·차감·팔레트 적재가 일어난다. 그래서 WO Flow 의 LOT 칩·작업지시별 LOT 전체 화면(`/pp/work-order/lots/{WO}`)에는 RAW 가 나오지 않고 **PP-LOT(「LOT 조회」, `pp/lot`)에서만** 보인다(작업지시 칸 「—」). 오래 남은 RAW 는 확정을 빠뜨렸거나 필요 없는 LOT 이다 — IMG·PNT 는 「발행 취소」(`VoidRawLot`, IMG)로 지우고 사출 RAW 는 스캔 확정하거나 불량 등록해 정리한다. 상태별 정리: RAW 미확정 · CONFIRMED 확정(실적 반영) · DEFECT 불량 등록(재작업 대기) · SCRAPPED 폐기 · NG_BLOCKED 로봇 NG 로 막음.
수리 양품은 `ReworkRepository.Rework` 가 원래 WO 에 `PR_ProductionResult` +1(`ProcessCode='RWK'`, `LineID='LINE-RWK-01'`) + `BumpStepCompleted(+1)` 로 확정한다. WO 는 등록 행의 `WoID` → 없으면 원래 라인 `FindOpenForItem` 순으로 해석하고, 둘 다 없으면 WO 없이 확정한다(`WoID` NULL, 단계 반영 없음 — WO 없는 생산분의 수리, 10-01). 폐기는 실적을 건드리지 않는다.
**IMG 가 완제품 코어로 이미 쓴 사출 LOT(`tbl_Lot.ParentLotID` 로 이어진 자식 있음)과 출하된 LOT(그 LOT·팔레트의 `FG_Shipment` 가 있고 양수 재고 행 없음)은 라인 불량으로 등록하지 않는다**(10-28 `DefectRegisterOutcome.UsedAsCore`·`Shipped`, 규칙 `LotDefectRules.CheckRegister(status, usedBy, shipped)`) — 완제품을 불량 처리하거나 고객 반품 검사로 다룬다. 불량 등록은 `tbl_Lot.Status` 도 DEFECT 로 바꾼다(수리 양품은 CONFIRMED, 폐기는 SCRAP). 확정 후 LOT 의 불량 등록은 `PR_ProductionResult` 역분개 행(`GoodQty=-1`, `DefectFlag=0` — 불량은 `PR_DefectDetail` 에 있다, 보고서 이중 계상 방지) + 단계 `CompletedQty −1` 이며, `BumpStepCompleted` 는 음수일 때 단계 `Closed → In Progress` 를 되돌리고 `ActualEnd` 를 지운다; 헤더는 그 단계가 마지막 라인 단계일 때만 같이 되돌린다(헤더 `CompletedQty` 를 움직이는 건 그 단계뿐이다). **불량으로 모자란 수량은 다음 스캔이 그 WO 에 채운다**(10-28 사용자 결정) — 다시 열린 단계는 In Progress 라 열린 WO 해석에서 Released WO 보다 먼저 잡히고, 다시 마감된 뒤에야 다음 WO 로 넘어간다(헤더가 이미 끝난 WO 는 받지 않는 규칙 그대로). **불량은 반드시 추적된다** — `PR_DefectDetail` 에 LOT·WO(확정 LOT 은 원래 실적의 WO, 확정 전 LOT 은 그 시점 열린 WO 또는 NULL)·원래 실적(`ResultID`)·역분개 실적(`ReversalResultID`, 같은 WO·LOT)이 남는다. 정본 테스트 `InjLotRepositoryTests.Defect_on_a_closed_wo_stays_traceable_and_the_next_scan_refills_that_wo`. 확정 전(RAW·NG_BLOCKED) LOT 의 불량은 실적 행이 없어 `PR_DefectDetail.ResultID` 가 NULL 이다 — **실적에 불량을 붙여 세는 집계는 이 행을 LOT 의 라인(`tbl_Lot.LineID`)·발생 전기일(`DetectedAt` − 경계 시각)로 따로 더한다**(10-13: RPT-001 `ListProductionByHour`·RPT-002 `ProductionTotals`·RPT 일정 준수 `ListScheduleWo`(WoID 있는 행만)·RPT-010 생산 실적·OEE `ComputeOee`(Q·P 모두), 이미 그렇던 RPT-002 파레토·RPT-008 월간·Api 일별 생산과 같은 귀속; RPT-010 불량 원본의 「라인」 차원도 10-14 부터 RPT-002 파레토와 같이 실적 라인 → 없으면 LOT 라인; 정본 테스트 `RptLotDefectTests`). 새 생산 집계도 `ResultID` 조인만으로 불량을 세지 말 것.
REWORK 로그인은 `LINE-RWK-01`(WC `WC-RWK`, ProcessCode `RWK`) 선택 — 마스터가 없으면 로그인 불가. `AppState.ModuleCode="RWK"` 라 `LabelDispatcher` 는 돌지 않는다. 대기열은 전 라인 공용이다.
