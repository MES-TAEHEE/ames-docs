## 알림 채널 — PUSH (10-08, 사용자 결정)

메일·SMS 발송이 불가능해 알림은 **내부 앱의 PUSH** 로 간다(앱은 별도 개발 예정). 단 나중에 다시 쓸 수 있게 **채널은 지우지 않고 공통코드 `NOTIFICATION_CHANNEL` 의 사용 여부(UseFlag)로만 켜고 끈다** — EMAIL·SMS 행은 사용 안 함으로 남기고 PUSH 만 사용. `dist/migrate_notification_push.sql`(재실행 안전 — **처음 적용할 때만 바꾼다**: PUSH 코드 행이 이미 있으면 아무것도 바꾸지 않아, 그 뒤 MD-030·SYS-008 에서 사람이 바꾼 채널·규칙을 되돌리지 않는다(10-09), 개발·로컬 적용 완료, `rebuild_db.sh` 끝)이 코드를 이렇게 맞추고(이전 이름 APP 이면 PUSH 로 개명) 알림 규칙 `SYS_NotificationRule.ChannelsJSON` 에 PUSH 를 **더한다**(EMAIL·SMS 는 그대로). 사용자별 채널(`SYS_NotificationChannel`)·발송 이력(`SYS_NotificationHistory`)·안돈 기록(`PR_AndonPush`)의 과거 EMAIL·SMS 값은 건드리지 않는다.
- **발송 원칙**: 규칙에 적힌 채널 중 **사용 중인 채널로만** 보낸다(앞으로 만들 발송기의 규칙). 메일·SMS 를 다시 쓰려면 MD-030 에서 UseFlag 를 켜고 발송 설정만 추가하면 기존 규칙·주소가 그대로 살아난다.
- **SYS-008 알림 관리**(`Sys/Notifications.razor`, 채널 공통코드를 쓰는 유일한 화면): 새로 고르는 채널 콤보는 사용 중인 채널만, 규칙 수정 창은 모든 채널을 보이되 사용 안 함 채널에 「비활성」 표시(선택돼 있으면 해제 가능, 새로 체크는 불가), 목록·이력의 사용 안 함 채널 칩은 흐림+취소선, 이력 채널 필터는 사용 안 함 채널까지 고를 수 있다. 사용 중 채널이 없을 때 EMAIL/SMS/KAKAO/SLACK 을 보이던 고정 대체 목록은 없앴다. **채널 설정의 PUSH 행은 웹에서 만들거나 주소를 바꾸지 않는다**(10-24 — 주소는 알림 앱이 로그인할 때 등록하는 FCM 토큰): 등록 창은 PUSH 를 고르면 주소가 꺼지고 등록 버튼이 꺼지며, 수정 창은 채널을 바꾸지 못하고(주소 종류가 채널에 묶임) PUSH 행 주소는 읽기 전용(수신 여부·방해금지 시각만), 저장소도 `InsertNotificationChannel` 이 PUSH 를 거부하고 `UpdateNotificationChannel` 은 PUSH 행의 수신자·채널·주소를 보존하며 다른 채널 행을 PUSH 로 바꾸지 않는다(정본 테스트 `NotificationChannelWebEditTests`). 채널 행의 수신자는 사번이라 등록 콤보는 사번 있는 계정만, 목록·이력은 `Actors.Display` 로 「이름 (사번)」을 보인다.
- **발송기 = AMES.Api 「NOTIFY」 Worker(FCM)**(10-24 사용자 결정 — 수신자 A안·FCM·PIN 없는 작업자는 앱 로그인 불가): `Workers/Notify/NotifyWorker`(`ScheduledWorker` 상속, 대상 하나 `PUSH`, 모니터 `SYS_InterfaceMonitor` `NOTIFY-PUSH` — 방향 OUTBOUND, `SysRepository.UpsertInterfaceMonitor(…, direction)`)가 주기마다 ① `NotificationRepository.EnqueuePush` — 이벤트 감지(고장 `FAILURE_OPEN`(열린 고장, 신고 뒤 `LOOKBACK_MIN` 안)·안돈 `ANDON_RAISED`·QC 홀드 `QC_HOLD`(Held)·PM 지연 `PM_OVERDUE`(취소 아닌 예정일 경과, 하루 한 번 — 원천 번호 `계획번호@yyyyMMdd`)·예비품 재고 부족 `LOW_STOCK`(재주문점 > 0 이고 현재고 ≤ 재주문점, 하루 한 번)) → 사용 중이고 채널에 PUSH 가 있는 규칙(`SYS_NotificationRule`) → 수신 역할의 **사번**(활성 웹 사용자(`AccountStatus` ACTIVE) + 규칙에 `ROLE-OPERATOR` 가 있으면 PIN 이 있는 활성 `MD_Worker` 전원, 같은 사번의 웹 계정이 있으면 웹 계정 쪽) → 그 사번의 사용 중 PUSH 기기(`SYS_NotificationChannel`, 주소 = FCM 토큰) → 기기마다 `SYS_NotificationHistory` 1행(PENDING, 방해 금지 시간 `QuietHoursStart/End` 안이면 QUIET — 보내지 않고 목록에만; 같은 (이벤트, 원천, 수신자, 기기)는 다시 만들지 않음, `sp_getapplock`) ② `ClaimDue` — PENDING·기다린 시간이 지난 FAILED(`MAX_RETRY`, 간격 2^n 분 최대 30)·10분 넘게 SENDING 인 행(하루 이내)을 READPAST 로 잡아 SENDING 으로 → `FcmSender`(FCM HTTP v1, 서비스 계정 JWT — 외부 패키지 없음) → SENT / FAILED(404·UNREGISTERED·토큰 오류 400 은 영구 실패 + 그 토큰 기기 행 끔). 개발서버·로컬 IIS Api 가 같은 DB 를 써도 감지는 applock, 발송은 행 잡기로 겹치지 않는다. 설정 공통코드 `SW_NOTIFY`(INTERVAL 1·LOOKBACK_MIN 60·MAX_RETRY 3·BATCH 100, `dist/migrate_notification_push_sender.sql` — 조회 인덱스 5개와 기존 채널·이력의 웹 사용자 ID → 사번 변환 포함, 재실행 안전, 10-24 개발·로컬 적용 — 채널 1·이력 40행 사번 변환, 스키마·`rebuild_db.sh` 반영), **FCM 서비스 계정 키는 Api 서버 파일**(appsettings `Notify:FcmServiceAccountPath` / 환경변수 `Notify__FcmServiceAccountPath` — 비우면 ①만 돌아 이력이 PENDING 으로 쌓이고 모니터는 ERROR). 앱 Api `/api/notifications`(`Endpoints/NotificationEndpoints`): `POST /devices`·`POST /devices/off`(토큰 등록·끄기 — 같은 토큰이 다른 사번에 있으면 옮긴다), `GET /`(목록 — (이벤트, 원천)마다 최신 1행, `unread`·`before`·`take`), `GET /{id}`(상세 — 원천의 **지금** 상태 `source` 를 붙인다: 고장·안돈·QC 홀드·PM·예비품마다 상태·발생/종료 시각·라인·설비·품목·심각도 + 종류별 항목 `fields[{key, value}]`(키는 영어 camelCase 고정 — 고장 증상·보고자·작업지시·담당자, 안돈 원인·책임자·부서 호출 단계, PM 예정일·작업지시, 예비품 현재고·재주문점 등), PM 상태는 `PmRules.DisplayStatus`, 상태형 이벤트의 `@날짜` 는 떼고 찾음, 원천이 없으면 null — `NotificationRepository.ReadSource`)·`POST /{id}/read`·`GET /unread-count`·`GET`/`PUT /quiet-hours`(방해 금지 시간 `{start, end}` HH:mm — **사람 단위**: 쓰면 그 사번의 PUSH 기기 행 전부, 새로 등록하는 기기는 그 사번의 설정을 이어받는다, 둘 다 비우면 해제, 한쪽만·형식 오류·같은 시각은 400, 기기가 없으면 404 — 규칙 `NotifyRules.TryParseQuietHours`). **PIN 로그인 세션만** 받는다(`POST /api/auth/login` — 배지 로그인 세션 403, PIN 없는 작업자는 로그인 자체가 안 된다), 자기 사번 행만. 한 번 등록한 기기는 세션이 끝나도 받는다(로그아웃은 알림을 끊지 않음 — 끄기는 `/devices/off`, 계정 사용 안 함·FCM 토큰 무효·같은 기기 다른 사번 로그인). 반복 알림(`ALERT_REPEAT_MINUTES`)·나머지 이벤트 4종(납기 위험·SAP·PLC·일일 요약)은 아직 없다(확인사항 오세영). 정본 `AMES.Data.Services.Notify.NotifyRules`(`NotifyRulesTests`), DB `NotificationRepositoryTests`(`AMES_TEST_CONN`), FCM 메시지 `FcmMessageTests`.
- 안돈 PUSH 는 발송기가 `PR_AndonCall` 을 보고 규칙대로 보낸다. POP 이 `PR_AndonPush` 에 고정 수신자(`SUPERVISOR/PDA`·`LINE-LEAD/EMAIL`)를 적던 임시 코드는 읽는 곳이 없어 10-28 지웠다(테이블·`SP_POP_ANDON_RecordPush` 는 구 Pop 용으로 남음).

## 외부 API 연동 Worker — AMES.Api

외부 시스템을 주기적으로 호출하는 연동(가져오기·내보내기)은 **API 마다 Worker 하나**를 두고, 모두 `AMES.Api/Workers/ScheduledWorker<TTarget, TResult>` 를 상속한다(첫 Worker 는 아래 PO Sync). 베이스가 가진 공통 규칙(정본 `AMES.Api.Tests/ScheduledWorkerTests`):

- 틱마다 `LoadPlan()` 을 다시 읽고(캐시 없음) 대상별 주기(`IntervalMinOf`, 0 이하는 그 대상만 중지)가 지난 것만 순차 실행. `ScheduledPlan.Enabled=false` 면 스케줄러 전체 중지(수동 실행은 허용).
- **시간 설정은 2단 — Worker 마다 다른 값은 공통코드, 공통 기본값은 appsettings**(정본 `ScheduledWorkerSettings`): 틱 간격·시작 지연은 `ScheduledPlan.TickSec`/`StartupDelaySec`(Worker 가 자기 공통코드에서 읽어 채움) → appsettings `ScheduledWorker:TickSec`(기본 60) · `ScheduledWorker:StartupDelaySec`(기본 10) 순, HTTP 타임아웃도 같은 방식으로 `ScheduledWorker:TimeoutSec`(기본 60). 범위 밖 값(틱·타임아웃 1 미만, 지연 음수)은 없는 것으로 본다. 고정 타이머가 아니라 **틱이 끝날 때마다 그 틱에서 읽은 계획으로 다음 대기**를 정하므로 틱 간격 변경도 다음 틱부터 반영되고, 틱 시작 간격은 실행 시간 + 틱 간격이다(계획 로드 실패 시 직전 값). 시작 지연을 정하려고 기동 때 계획을 한 번 읽으며, 실패하면 공통 기본값으로 기다린다.
- 마지막 실행 시각은 메모리라 Api 재시작 직후 모든 대상이 한 번 돈다. 대상별 잠금으로 틱과 수동 실행이 겹치지 않는다.
- 수동 실행 `RunNowAsync(key)`: 대상별 60초 쿨다운(틱 실행도 시계를 채운다). 단건은 미등록 키 404 · 진행 중/쿨다운 409, 전체 실행은 해당 대상을 결과 안에 `busy`/`cooldown` 으로 담고 나머지는 계속. 엔드포인트는 자기 경로·쿼리 이름을 유지하고 `ScheduledWorkerEndpoints.RunAsync` 한 줄로 이 HTTP 규칙을 쓴다(세션 없으면 401). POP 세션이 없는 AMES.Web 이 부를 길은 **서비스 키**다 — 엔드포인트가 `RunAsync` 에 키 공급자(`Func<string?>`)를 넘길 때만 열리고, 헤더 `X-AMES-Service-Key` 가 공급자 값과 일치(`FixedTimeEquals`)해야 통과한다. 공급자가 null·빈 값을 주거나 예외를 내면 닫힌 채(401)이고, 헤더가 없거나 세션이 있으면 공급자를 부르지 않는다(정본 `ScheduledWorkerEndpointsTests`).
- 계획 로드 자체가 실패(DB 접속 등)하면 모니터 행 `{Code}-CONFIG` 에 남기고 예외를 다시 던진다. 대상 모니터 행 `{Code}-{키}` 는 20자(`SYS_InterfaceMonitor.InterfaceCode`)를 넘지 않게 Worker 가 키 길이를 제한한다.
- **공통코드 그룹 이름 규칙**: Worker 설정 그룹은 모두 **`SW_{Code}`** 로 시작한다(`SW_{Code}` 전역 · `SW_{Code}_SOURCE` 등) — MD-26 그룹 검색(GroupCode·이름 부분 일치)에 `SW_` 를 넣으면 모든 Worker 설정이 나온다. 그룹 이름(한·영)에는 접두어를 붙이지 않는다(예 `PO 자동수집 설정` / `PO Sync Settings` — 10-05 사용자 결정, 구 규칙 `ScheduledWorker · ` 접두어는 폐지). `MD_CodeGroup.GroupCode` 가 VARCHAR(20) 이라 `_SOURCE` 를 붙이는 Worker 는 `Code` 를 10자 이내로 둔다. 그룹 이름 상수는 도메인 설정 클래스 한 곳에 두고 `"SW_" + Code` 에서 파생한다(PoSync: `PoSyncConfig.GroupGlobal` 등).
- **새 API 추가**: `Workers/{이름}/{이름}Worker` 가 베이스를 상속해 `Code`·`Name`·`LoadPlan`·`KeyOf`·`IntervalMinOf`·`RunTargetAsync`·`RecordConfigError`·`Skipped`·`IsOk` 를 구현 → `Program.cs` 에 `AddSingleton<X>()` + `AddHostedService(sp => sp.GetRequiredService<X>())`(엔드포인트가 같은 인스턴스를 주입받아야 한다) → 엔드포인트 한 줄. 도메인 로직(설정 해석·매핑·실행기)은 `AMES.Data.Services.{이름}` 에 두고 `AMES.Data.Tests` 에서 테스트한다.
- Worker 마다 타이머가 따로 돌고 **Worker 간 실행 순서 조율은 없다**(API 마다 Worker 를 두기로 한 결정의 대가).

## PO 자동 수집 (PO Sync) — AMES.Api

고객사 SRM 의 MM31006 `INQUERY` 결과를 REST 로 받아 PP-002 와 같은 `PpRepository.UpsertCustomerOrders` 로 `PP_CustomerOrder` 에 업서트한다(actor `PO-SYNC`, 새 행 `Open`, 확정은 PP-002 에서). `AMES.Api/Workers/PoSync/PoSyncWorker`(위 `ScheduledWorker` 상속, `Code=POSYNC`)가 돌리며 설정은 전부 **공통코드(MD-26)** 다 — 주기·고객사·URL·인증 토큰까지. 마이그레이션 `dist/migrate_po_sync.sql` 은 그룹 4개와 전역 기본값만 만든다(재실행 안전). 09-17 에 그룹을 `PO_SYNC*` → `SW_POSYNC*` 로 바꿨고, 구 이름으로 적용된 DB 는 같은 스크립트를 다시 돌리면 항목을 새 그룹으로 옮기고(CodeID 접두어 포함) 빈 구 그룹을 지운다. URL·토큰이 긴 값이라 공용 `dist/migrate_md_codeitem_widen.sql`(`Attribute1` 200 · `Description` 500)이 먼저 적용돼 있어야 MD-26 에서 저장된다. 이게 없으면 워커는 소스 0개로 돌 뿐 예외는 없다.
