단위 테스트 11/4 – 11/6 → 전체 흐름(E2E) 1주 11/9 – 11/13 → 고객 회의 11/16 (주말 11/7·8·14·15 제외)

확인 필요 항목 (내일 확인 예정)

문서로 기능 유무나 절차가 확정되지 않은 항목입니다. 확인 후 시나리오를 고치고 이 목록에서 뺍니다. 항목을 누르면 해당 시나리오로 이동합니다.

    1. 테스트 원칙

    1. 순서: 단위 테스트(0~16)를 모두 끝낸 뒤에만 전체 흐름(17)을 시작한다. 전체 흐름은 1주간(11/9 – 11/13) 진행한다. 단위 중 실패는 모듈을 고쳐 재시험하고, 보류 항목은 사유를 적는다.
    2. 단위 테스트의 CRUD 순서: 생성(C) → 조회(R) → 수정(U) → 삭제(D) → 잘못된 입력 거부(N) 순으로 확인한다. 각 항목의 「관련 데이터」와 「확인할 로그」를 함께 본다.
    3. 전체 흐름의 순서: 수주 → 일별 계획 → 생산계획(APS·WO·슬롯) → 구매(MRP·PR·PO) → 입고 → 생산(사출·IMG·PNT) → 재작업·품질 → 설비보전 → 출하(오더·DCR·출고) → 공급사 Portal 납품과 우리 PDA 입고 → 빈 팔레트 회수·재사용 → 보고·재고 정합 → 로그 전수 확인. 공급사 납품은 고객 출하와 별개의 문서로 연결한다.
    4. 번호 연결: 앞 단계가 만든 번호(수주 번호·WO 번호·PR 번호·PO 번호·LOT 번호·팔레트 번호·DCR 번호·출하 번호)를 다음 단계 입력으로 쓴다.
    5. 로그 확인: 데이터가 바뀔 때마다 감사 로그·재고 거래 이력·현장 로그 파일·연동 모니터 중 해당 기록을 확인한다. 기록이 없으면 결함이다(16번 그룹 참고).
    6. 실패 처리: 결함 번호, 재현 절차, 확인한 로그 위치, 화면 캡처를 비고에 적는다. 실패 단계 이후는 보류로 두고, 수정 뒤 그 단계부터 다시 실행한다.
    7. 데이터: 테스트 전용 ID(TST-…)만 쓴다. 실제 고객 정보와 실제 사번은 쓰지 않는다. 시험 계정은 조회 전용·수정·승인 권한을 나눠 쓴다.
    8. 일정: 주말 작업은 하지 않는다.

    2. 일정 (간트)

    막대나 행 이름을 누르면 해당 시나리오 그룹으로 이동한다.

    3. 테스트 시나리오

    그룹 → 시나리오 순서로 접고 펼쳐 본다. 결과 칸과 비고는 이 브라우저에 저장되며, 취합은 「결과 내보내기」 파일로 한다.
    작성 기준: 현행 시스템 기능 명세와 공정 흐름. 항목 번호는 화면 ID(예 PP-002, INJ-MAIN)와 맞춘다. 확인 필요(노란 표시) 항목은 기능 유무나 절차가 문서로 확정되지 않은 것이며, 확인 후 시나리오를 갱신한다.
