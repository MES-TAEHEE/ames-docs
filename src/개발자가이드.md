A-MES 개발 컨벤션 & Git 운영 규칙

개발 컨벤션 + Git 운영 규칙 정의서

본 문서는 A-MES 프로젝트에서 사용하는 개발 컨벤션 + Git 운영 규칙을 정의합니다.
적용 범위: API(.NET) / Frontend(React) / DB(MSSQL) / 문서(README/ADR)
Git 전략: GitHub Flow (main + feature/ + hotfix/)

1) 목적
•  팀 내 코드 품질 / 가독성 / 유지보수성 확보
•  PR 기반 협업 표준화 (리뷰 / 테스트 / 릴리즈)
•  배포 / 핫픽스 / 롤백 시 사고 최소화

2) 저장소 / 브랜치 전략 (GitHub Flow)
2.1 기본 원칙
•  main은 항상 배포 가능한 상태를 유지
•  모든 변경은 feature / hotfix 브랜치에서 작업 후 PR로 main에 병합
•  PR 병합은 CI 성공 + 최소 1인 리뷰 승인을 원칙으로 함
2.2 브랜치 네이밍
•  기능: feature/<topic>
–  예) feature/pp-mrp-blocking, feature/sys-rbac-ui
•  버그 / 수정: fix/<topic>
–  예) fix/qc-gate3-nullref
•  핫픽스(운영 긴급): hotfix/<topic>
–  예) hotfix/login-deadlock
•  문서: docs/<topic>
–  예) docs/api-conventions
•  실험 / POC: chore/<topic> 또는 spike/<topic>
2.3 커밋 단위
•  “작게, 자주” (리뷰 가능한 단위)
•  한 커밋에는 한 가지 목적만
•  빌드가 깨지는 커밋은 금지 (부득이하면 PR에서 squash)

3) 커밋 메시지 규칙
•  권장: Conventional Commits 형태
–  feat: 기능 추가
–  fix: 버그 수정
–  refactor: 리팩토링 (동작 변화 최소)
–  perf: 성능 개선
–  test: 테스트 추가 / 수정
–  docs: 문서 변경
–  chore: 빌드 / 도구 / 의존성
–  ci: CI 설정
–  style: 포맷 / 정렬 (로직 변경 없음)
예시
feat(pp): add MRP shortage blocking rule
fix(qc): prevent null inspection result on gate3
refactor(sys): split auth middleware
docs: update deployment checklist

4) PR(풀리퀘스트) 규칙
4.1 PR 제목
•  [모듈] 요약 형태 권장
–  예) [PP] MRP 차단 로직 추가
4.2 PR 본문 체크리스트
•  변경 배경 / 목적
•  주요 변경점 (요약)
•  테스트 방법 / 결과 (로컬 / 단위 / E2E)
•  영향 범위 (API / DB / UI / 배치)
•  롤백 방법 (필요 시)
4.3 리뷰 기준
•  로직 정합성 (BR / 요구사항 충족)
•  예외처리 / 로깅 / 보안 (OWASP) 고려
•  성능 영향 (쿼리 / 인덱스 / 캐시)
•  가독성 / 네이밍 / 중복 제거
•  테스트 충분성 (단위 / 통합)
4.4 병합 방식
•  기본: Squash merge
•  히스토리 보존이 중요 (릴리즈 / 핫픽스): Merge commit 허용

5) 릴리즈 / 태깅 / 버전
•  릴리즈 태그: v<major>.<minor>.<patch>
–  예) v1.3.0, v1.3.1
•  운영 배포는 태그 기준으로 추적 가능해야 함
•  변경 로그(Release Notes)는 PR 목록 + 주요 이슈 / 리스크로 작성

6) 코드 컨벤션 (.NET / C#)
6.1 네이밍
•  클래스 / 메서드 / 프로퍼티: PascalCase
•  로컬변수 / 파라미터: camelCase
•  인터페이스: I... (예: IWorkOrderService)
•  비동기 메서드: ...Async
6.2 예외 처리
•  Controller에서 try / catch 남발 금지
•  Global Exception Handler / 미들웨어로 일원화
•  사용자 메시지와 로그 메시지 분리
6.3 DTO / Response
•  Response는 BaseResponse 규칙 유지
•  Validation은 FluentValidation 등으로 계층 분리
6.4 EF Core / DB
•  N+1 방지: Include / Projection 명확히
•  트랜잭션 필요 시 명시적으로 사용
•  마이그레이션은 항상 Down() 구현 (롤백 가능)

7) 프론트엔드 컨벤션 (React + TS)
7.1 폴더 / 파일
•  기능 기준(모듈)으로 페이지 / 컴포넌트 구성
•  재사용 컴포넌트는 /components/common
7.2 상태 / 데이터 패칭
•  서버 상태는 Query 라이브러리(또는 표준 훅)로 일원화
•  에러 / 로딩 상태는 화면 표준 컴포넌트로 통일
7.3 UI 규칙
•  권한 없는 메뉴는 미표시 (RBAC)
•  POP / PDA는 터치 UI 우선 (최소 44px)

8) 테스트 전략
•  단위 테스트: 핵심 BR / 도메인 로직 우선
•  통합 테스트: API + DB 시나리오
•  E2E: 핵심 공정(WH → PP → 생산 → QC → FG) 시나리오
•  버그 수정 시 회귀 테스트 추가 원칙

9) 보안 / 품질 기본 원칙
•  인증 / 인가: JWT + Role 기반 접근 제어
•  입력 검증 필수 (서버 측)
•  SQL Injection 방지: 파라미터화 / ORM 규칙 준수
•  민감정보는 환경변수로 분리

10) 문서 / 산출물 운영
•  변경이 있는 기능은 최소한의 문서 업데이트 포함 (README / 가이드 / ADR)
•  “왜(Why)”가 있는 결정은 ADR로 남김
